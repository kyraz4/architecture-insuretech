# Task1. Проектирование технологической архитектуры

## Требования бизнеса

- Бесперебойная работа 24/7 для клиентов из всех часовых поясов РФ.
- Высокая отказоустойчивость: **RTO — 45 мин**, **RPO — 15 мин**.
- Доступность приложения — **99,9%**.
- Одинаковое время загрузки страниц для пользователей из разных регионов, независимо от геолокации.
- Объём данных в системе — **50 GB** (данные клиентов, продукты и тарифы, история заявок).

## Архитектурные решения

### 1. Стратегия масштабирования

Выбрано **горизонтальное масштабирование**, а не вертикальное. Причины:

- вертикальное масштабирование не решает требование геораспределённости и одинакового времени загрузки для пользователей из разных регионов;
- вертикальное масштабирование имеет физический потолок и создаёт single point of failure;
- горизонтальное масштабирование в Kubernetes (несколько реплик каждого сервиса + автомасштабирование групп узлов) даёт устойчивость к отказу пода, узла и целой зоны доступности.

### 2. Зоны доступности

Используются **три зоны доступности**: `ru-central1-a`, `ru-central1-b`, `ru-central1-d`.

Это минимально необходимое количество для соблюдения SLA 99,9% и RTO 45 мин: при отказе одной зоны система продолжает работать на двух оставшихся без деградации.

### 3. Kubernetes: один региональный кластер

Выбран **один кластер Managed Service for Kubernetes** с Control Plane, размещённым в трёх зонах доступности, и группами узлов (Node Groups) в каждой зоне.

Почему не независимые кластеры в каждой зоне:

- независимые кластеры усложняют управление, деплой и наблюдаемость;
- не дают преимуществ при RTO 45 мин — переключение между кластерами всё равно потребует времени;
- один региональный кластер с HA-мастером покрыт SLA Yandex Cloud и даёт требуемый уровень отказоустойчивости.

Дополнительно в кластере применяются:

- `Pod AntiAffinity` и `topology spread constraints` — чтобы реплики одного сервиса не оказывались в одной зоне;
- `PodDisruptionBudget` — для безопасных обновлений и планового обслуживания.

### 4. Балансировка нагрузки и health check

- **Application Load Balancer (L7)** принимает трафик из интернета и распределяет его между подами `core-app` во всех трёх зонах доступности.
- **Health check**: `GET /health`, интервал ≤ 3 секунды. Нездоровые поды автоматически исключаются из балансировки, что ускоряет фейловер на уровне приложения.
- **Yandex Cloud CDN** кеширует статику (JS, CSS, изображения) в точках присутствия по РФ — это прямое решение требования «одинаковое время загрузки независимо от региона». При промахе кеша CDN идёт к origin (ALB).

### 5. Фейловер-стратегия

- **Уровень приложения**: Kubernetes пересоздаёт поды в здоровых зонах при отказе пода, узла или целой зоны — за счёт anti-affinity и topology spread constraints.
- **Уровень БД**: Managed PostgreSQL с мастером и репликами в разных зонах. При отказе мастера Yandex Cloud автоматически повышает реплику. Время переключения укладывается в RTO 45 мин.
- **Уровень подключения**: приложение подключается к **FQDN кластера**, а не к конкретной ВМ. При фейловере FQDN переключается на нового мастера автоматически — конфиги приложений менять не нужно.

### 6. Конфигурация PostgreSQL

- **Три инстанса в трёх зонах доступности**: master (зона A), sync replica (зона B), async replica (зона D).
- **Репликация**: master → sync replica (синхронная, RPO ≈ 0 для подтверждённых транзакций); master → async replica (асинхронная).
- **Бэкапы и PITR**: непрерывное WAL-архивирование + автоматические бэкапы с retention ≥ 7 дней. Это обеспечивает RPO ≤ 15 мин и возможность восстановления на любую точку в пределах retention.
- **Почему три инстанса, а не два**: при отказе любой одной зоны остаётся два инстанса — HA сохраняется. При схеме «мастер + одна реплика» отказ зоны с репликой оставляет мастер без синхронной реплики, а отказ зоны с мастером — систему с одним инстансом, что уже не HA.
- **Шардирование не применяется**: объём данных 50 GB, Managed PostgreSQL справляется вертикальным масштабированием с большим запасом. Шардирование на этом этапе добавило бы сложности без пользы.

### 7. Соответствие требованиям

| Требование | Как обеспечивается |
|---|---|
| RTO 45 мин | Автоматический фейловер Kubernetes и Managed PostgreSQL |
| RPO 15 мин | Синхронная репликация + PITR (WAL-архивирование) |
| Доступность 99,9% | Три зоны доступности, отсутствие single point of failure |
| Одинаковое время загрузки из разных регионов | CDN для статики + ALB для динамики |
| Бесперебойная работа 24/7 | Горизонтальное масштабирование, health check, автофейловер |
