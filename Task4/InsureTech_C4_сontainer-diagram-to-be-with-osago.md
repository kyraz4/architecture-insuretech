# Task4. Проектирование продажи ОСАГО

## Содержимое директории

- `InsureTech_C4_osago_to-be.puml` — обновлённая C4-диаграмма контейнеров (доработка схемы из Task3 с добавлением `osago-aggregator`).
- `README.md` — этот файл с обоснованием архитектурных решений.

## Контекст

Компания запускает онлайн-оформление ОСАГО. Пользовательский путь:

1. Клиент заполняет заявку с данными автомобиля.
2. Сервис запрашивает предложения у всех доступных страховых компаний.
3. Предложения от каждой компании отображаются на экране **сразу, как только от неё пришёл ответ**.
4. Максимальное время ожидания решения от одной компании — **60 секунд**.
5. Пик нагрузки — до **2500 одновременных пользователей**, создающих заявку.

Все страховые компании предоставляют однотипные REST API с двумя эндпоинтами:
- создать заявку на ОСАГО;
- получить предложение по заявке.

Принятые командой решения:
- сохранить подход, использованный для получения данных о продуктах и тарифах (Event-Driven из Task3);
- выделить отдельный сервис `osago-aggregator` для взаимодействия со страховщиками;
- вся остальная функциональность оформления ОСАГО остаётся в `core-app`.

## Архитектурные решения

### 1. Хранилище `osago-aggregator`

**Нужно собственное хранилище — PostgreSQL (`osago-db`), отдельная схема.**

Причины:
- **Состояние заявки.** Агрегатор рассылает заявку в 10 компаний и опрашивает каждую до 60 секунд. Нужно хранить: id заявки, какие компании уже ответили, какие ещё нет, полученные предложения, таймауты.
- **Идемпотентность.** При 2500 одновременных пользователях и retry-политике возможны повторные вызовы «создать заявку». Нужен idempotency key, чтобы не создавать дубли у страховщика.
- **Устойчивость к рестартам.** Агрегатор задеплоен в нескольких экземплярах. Если экземпляр упадёт, состояние заявки не должно потеряться.
- **Разгрузка `core-app`.** `core-app` не должен хранить промежуточное состояние опроса 10 компаний — это чужая зона ответственности.

Схема таблиц:
- `osago_requests` — id, client_id, car_data, status, created_at;
- `osago_request_offers` — request_id, insurer_id, status, offer_payload, received_at;
- `idempotency_keys` — ключ, request_id, created_at.

### 2. API `osago-aggregator` для `core-app`

- **`POST /osago/requests`** — создать заявку. Принимает данные автомобиля и клиента, возвращает `request_id` сразу (`202 Accepted`). Дальше агрегатор асинхронно рассылает заявку по компаниям.
- **`GET /osago/requests/{request_id}`** — получить текущее состояние: какие компании уже ответили, какие предложения получены. Используется `core-app` при переподключении WebSocket или для восстановления состояния.

Предложения доставляются в `core-app` **через Event Bus** (топик `osago.offers.ready`), а не через синхронный polling. Это сохраняет Event-Driven подход из Task3 и не возвращает систему к синхронной модели.

### 3. Интеграция `core-app` ↔ `osago-aggregator`

**Event-Streaming через Event Bus** для доставки предложений + **REST** для создания заявки и запроса состояния.

- Создание заявки — REST `POST /osago/requests`: команда с немедленным ответом (нужен `request_id`).
- Предложения — событие `osago.offers.ready` в Event Bus. Как только страховая компания ответила, агрегатор публикует событие с `request_id` и предложением. `core-app` подписан и передаёт предложение в веб-приложение.
- Это обеспечивает требование «предложения отображаются сразу, как только от компании пришёл ответ» — без ожидания самой медленной компании.

### 4. API для веб-приложения в `core-app`

Два канала:

- **REST** — для создания заявки, получения истории и прочих операций: `POST /api/osago/requests`, `GET /api/osago/requests/{id}`.
- **WebSocket** — для стриминга предложений в реальном времени: `wss://core-app/api/osago/requests/{id}/offers`. Клиент подписывается после создания заявки и получает каждое предложение по мере поступления.

Почему WebSocket, а не SSE или long polling:
- WebSocket поддерживает двусторонний канал и хорошо масштабируется при 2500 одновременных пользователях.
- SSE тоже подошёл бы, но WebSocket уже используется в проекте для других real-time сценариев — единообразие.
- Long polling создаёт лишнюю нагрузку на `core-app` при пике.

### 5. Паттерны отказоустойчивости

| Паттерн | Где применяется | Зачем |
|---|---|---|
| **Rate Limiting** | Вход в `core-app` для B2B-партнёров и веб-клиентов | Защита от «съедания» ресурсов одним партнёром (проблема из вводной) |
| **Timeout** | Все синхронные вызовы: `core-app → client-info`, `core-app → payment`, `core-app → osago-aggregator`, `osago-aggregator → страховщики`, `ins-product-aggregator → страховщики`, `ins-comp-settlement → страховщики` | Для страховщиков — 60 секунд (требование бизнеса), для внутренних вызовов — меньше |
| **Retry** | Идемпотентные вызовы: создание заявки (с idempotency key), получение предложения, вызовы `client-info` и `payment` | Экспоненциальный backoff, ограниченное число попыток |
| **Circuit Breaker** | Каждый страховщик отдельно (в `osago-aggregator` и `ins-product-aggregator`), внутренние вызовы `core-app → client-info`, `core-app → payment` | При 10 компаниях отказ одной не блокирует остальные |

### 6. Учёт мультиэкземплярности сервисов

Решение учитывает, что сервисы задеплоены в нескольких экземплярах:

- **Event Bus** — ключевой элемент. Предложения от `osago-aggregator` публикуются в топик `osago.offers.ready` с ключом `request_id`. Kafka гарантирует, что все экземпляры `core-app` в одной consumer group получат события, но каждое событие обработает ровно один экземпляр. Это позволяет горизонтально масштабировать `core-app`.
- **WebSocket** — при нескольких экземплярах `core-app` клиент подключён к одному из них. Чтобы предложение дошло до нужного экземпляра, используется pub/sub через Event Bus: каждый экземпляр `core-app` подписан на `osago.offers.ready` и держит локальный реестр активных WebSocket-сессий по `request_id`. Событие получает тот экземпляр, у которого есть сессия. Если сессий нет — событие сохраняется в `core-db` и отдаётся при переподключении.
- **`osago-aggregator`** — состояние заявки в `osago-db` (общая БД для всех экземпляров), поэтому любой экземпляр может продолжить опрос. Требуется идемпотентность и блокировки на уровне БД (например, `SELECT ... FOR UPDATE SKIP LOCKED`).
- **Transactional Outbox** — обязателен: при нескольких экземплярах нельзя полагаться на публикацию «в памяти». Outbox-таблица в `osago-db` и `core-db` гарантирует, что событие не потеряется при падении экземпляра между записью и публикацией.

### 7. Топик `osago.offers.ready`

- **Ключ сообщения** — `request_id`.
- **Значение** — `{request_id, insurer_id, offer_payload, received_at}`.
- **Retention** — достаточный, чтобы клиент мог переподключиться и получить пропущенные предложения (например, 1 час). Дополнительно `core-app` сохраняет полученные предложения в `core-db` для истории.

## Соответствие требованиям бизнеса

| Требование | Как обеспечивается |
|---|---|
| Предложения отображаются сразу, как только пришёл ответ | Event Bus + WebSocket: агрегатор публикует `osago.offers.ready` по каждой компании отдельно, `core-app` стримит в веб |
| Максимальное ожидание от компании — 60 секунд | Timeout 60 секунд на вызове `osago-aggregator → страховщик` |
| Пик 2500 одновременных пользователей | Горизонтальное масштабирование `core-app` и `osago-aggregator`, Event Bus с consumer group, состояние в общей БД |
| Устойчивость к отказу одной компании | Circuit Breaker по каждой компании отдельно |
| Защита от «съедания» ресурсов одним партнёром | Rate Limiting на входе в `core-app` |
| Согласованность данных при сбоях | Transactional Outbox в `core-app` и `osago-aggregator` |

## Что изменилось по сравнению с Task3

1. Добавлен контейнер `osago-aggregator` с собственным хранилищем `osago-db`.
2. Добавлен топик `osago.offers.ready` в Event Bus.
3. Добавлена интеграция `core-app → osago-aggregator` (REST для создания заявки, Event Bus для предложений).
4. Добавлен WebSocket-канал между веб-приложением и `core-app` для стриминга предложений.
5. На схеме отмечены четыре паттерна отказоустойчивости: Rate Limiting, Timeout, Retry, Circuit Breaker.

Декомпозиция функциональности между существующими сервисами не менялась — добавлен только новый сервис `osago-aggregator`, как и было решено командой.
