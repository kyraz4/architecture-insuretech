# Task5. Проектирование GraphQL API

## Содержимое директории

- `client-info.graphql` — GraphQL-схема, эквивалентная REST API сервиса `client-info`.
- `README.md` — этот файл с анализом контракта и обоснованием схемы.

## Анализ Swagger-контракта

Исходный REST API `client-info` (Swagger 2.0, basePath `/v1`) содержит три ресурса:

| Ресурс | Метод | Что возвращает | Тип ответа |
|---|---|---|---|
| `/clients/{id}` | GET | Информация о клиенте | `Client` |
| `/clients/{id}/documents` | GET | Список документов клиента | `Document[]` |
| `/clients/{id}/relatives` | GET | Список родственников клиента | `Relative[]` |

Сущности:
- **Client** — `id`, `name`, `age`;
- **Document** — `id`, `type`, `number`, `issueDate`, `expiryDate`;
- **Relative** — `id`, `relationType`, `name`, `age`.

Ключевые наблюдения:
1. **Все три ресурса — это части одной карточки клиента.** `documents` и `relatives` — вложенные коллекции `Client`, но в REST они вынесены в отдельные эндпоинты.
2. **Вариативность запросов.** В разных сценариях нужны разные подмножества данных: где-то только имя и возраст, где-то — документы, где-то — родственники. REST заставляет делать несколько запросов, чтобы собрать нужный набор.
3. **Нет единого ресурса «вся карточка».** Как сказано в задании, отдавать все 500 атрибутов одним ответом нельзя — это замедлит взаимодействие, особенно с веб-приложением.

## Решение: GraphQL-схема

### Сущности

В GraphQL те же три типа: `Client`, `Document`, `Relative`. Отличие в том, что `Document` и `Relative` становятся **вложенными полями** `Client`, а не отдельными корневыми ресурсами:

```graphql
type Client {
  id: ID!
  name: String
  age: Int
  documents: [Document!]!
  relatives: [Relative!]!
}
